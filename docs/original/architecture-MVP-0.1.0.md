# Мультиагентная архитектура — развитие

## Сценарий

Telegram private / authorized group -> privacy filter -> Manager -> Plan (1–3 roles) -> Specialists in parallel -> Manager synthesis -> Telegram reply. Только пользовательское входящее обращение может вызвать ответ. Сложные внешние действия (создать задачу в CRM, отправить коммерческое предложение, опубликовать) пока не реализованы, позже — через отдельный шлюз с правами и подтверждением.

## Следующие модули (отдельный план, НЕ реализованы)

1. **База знаний** с актуальными карточками SYMMETLINE и FAQ KOMPREL; каждое утверждение о наличии/цене/доставке сопровождается источником и датой актуальности.
2. **Режимы и область полномочий:** публичный/клиентский bot; приватный управленческий chat. Коммерчески чувствительная аналитика доступна только разрешённым Telegram IDs, не участникам сторонних групп.
3. **Подключаемые действия** через n8n вебхуки: создание черновика задачи, запрос данных, подготовка отчёта. `dry_run`, audit, allowlist destinations, human approval для внешних изменений.
4. **Память и проекты**: SQLite/PostgreSQL с retention policy и отдельными пространствами команд; без хранения непричастных сообщений из групп.
5. **Роли**: добавить PPC, CRM, разработчик, визуальный генератор при появлении соответствующих инструментов. Каждая роль получает ограниченную область видимости, не все секреты.
6. **Модерация и QA**: чувствительные вопросы на ручную проверку, стоп-фразы, rate limits, настройка реакции на просьбы прекратить диалог, защита от bot loops.
7. **Наблюдаемость**: PostHog AI Observability (минимизация данных), cost/call, latency, качество ответов, события ручного согласования.
8. **Распределение долгих задач**: Celery/Redis/worker, очередь и статусы; текущая версия исполняет только синхронные по пользовательскому запросу ответы.

## Два контура (рекомендация)

**Внешний — помощник для клиента:** support / content; нет доступа к закрытой аналитике, базе клиентов и внутренним проектам. В разрешённых группах только реакции на @mention/reply/команды.

**Внутренний — управляющий командой:** management, marketing, design, analytics, seo, research; доступ только владельцу и сотрудникам в отдельном приватном чате; впоследствии подключение к рабочим источникам через ограниченные инструменты.

Эти два контура НЕ должны делиться историей и секретами даже при использовании одного Telegram Bot API аккаунта.

## Таблица распределения

- «Нужен баннер для рюкзака с УТП» -> marketing + design + content.
- «Почему реклама дороже в этом месяце?» -> analytics + marketing (только по фактическим данным).
- «Переделать главную для KOMPREL» -> design + marketing + seo.
- «Когда привезут заказ?» -> support (только доступный API/передача человеку).
- «Что обсуждают в Telegram о рюкзаках?» -> research (разрешённые публичные источники и ограничения, не чтение чужих чатов).

## Принцип выхода

Всегда один итоговый ответ пользователю. Можно указать, какие роли работали. Если данных нет, должен быть запрос конкретных исходных данных, а не домыслы. Внутренний журнал не хранит исходный текст запроса по умолчанию.
