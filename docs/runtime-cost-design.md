# Спецификация: лимиты LLM и бюджет Telegram AI Team

Статус: ТЗ для этапов 03/06, **не реализовано** в MVP v0.1.0.

### Логика выбора агентов
- /start, /help, /privacy, /stop, /human и простые ответы без LLM: без вызова модели.
- До LLM выполнить Telegram allowlist, RBAC, согласие и rate limit.
- Один специалист по умолчанию, управляющий как оркестратор (без LLM-планирования, если роутинг однозначен).
- Сложная задача: можно 2–3 специализированных вызова в рамках лимита; запрет на автоматический fan-out всем ролям.
- Суммарный ответ собрать без дополнительного LLM, если результат не требует согласования конфликтов; при конфликте — явно указать его, не выдумывать решение.
- Роли не выполняют скрытых дополнительных обращений/цепочек. Любой инструмент учитывается в бюджете вызовов.

### Обязательные настройки (точные имена согласовать и реализовать на этапе 03)
- `MAX_LLM_CALLS_PER_REQUEST` — верхняя граница вызовов;
- `MAX_ROLES_PER_REQUEST` — максимальное число специалистов;
- `MAX_OUTPUT_TOKENS` — ограничение объёма генерации;
- `MAX_CONTEXT_MESSAGES` — ограниченное окно недавних сообщений;
- `REQUESTS_PER_USER_PER_DAY`, `REQUESTS_PER_GROUP_PER_DAY` — квоты;
- `LLM_REQUEST_TIMEOUT_SECONDS` и `LLM_MAX_RETRIES` — исключить бесконечные повторы.

В `.env.example` добавлять только безвредные примеры значений после тестов; **не считать эти переменные уже существующими в коде**.

### Измерение, безопасность и качество
- Из API `usage` собирать `input_tokens`, `output_tokens`, `total_tokens` если доступны. При недоступности — `unknown`, не придумывать.
- Метаданные: route, role, model, дата, длительность, статус, количество вызовов. Не писать полные сообщения и секреты в логи по умолчанию.
- Разделить эксплуатационные квоты public/admin, приватные кэши и контекст между пользователями; общий кэш только для обезличенной публичной справки с TTL и версией.
- До релиза тестами доказать: простая команда — 0 LLM; простое обращение — не более 1 вызова к агенту (кроме явно обоснованной маршрутизации); сложное — не более настроенного потолка; запрос после превышения бюджета — 0 LLM.
- Проверить качество на фиксированных примерах, включая отказ по правам, отсутствующие факты о товаре, prompt injection и конфликт между специалистами.

Оптимизации не должны ухудшать качество критичных ответов или менять модель без отдельного подтверждения владельца.
