# Token economy — обязательная политика проекта

## A. Экономия при разработке в Codex
1. Один этап за обращение: не выполнять соседние задачи. На старте не перечитывать весь handoff; `AGENTS.md` + `CURRENT-STATE.md` + выбранный `phases/XX-*.md` достаточно.
2. Search → narrow read → patch → narrow test → stop. `rg`/`git diff --stat`/точечные диапазоны вместо печати всего каталога. Не включай `.venv/`, `__pycache__/`, `data/`, `*.log`, `.pytest_cache/` в контекст.
3. Не открывать весь OSINT и Telegram skills для обычной правки Python. Открывать один применимый `SKILL.md`, reference — только по потребности. Не загружать историю переписки заново.
4. Короткий ответ: что изменено; команда теста и результат; что не проверено; блокер/следующий шаг. Без повторов ТЗ, больших простыней кода и необоснованных рассуждений. При необходимости безопасности — полное объяснение.
5. Изменяй только нужные файлы; не переписывай модули целиком и не выполняй масштабный рефакторинг без разрешения. Ошибки и логи — небольшой релевантный фрагмент, но не искажать оригинальные сообщения.
6. Не запускать несколько LLM-агентов/Codex subagents ради простого чтения или маленького патча. Для независимых подзадач — только когда экономия подтверждена результатом, а не интуицией.
7. Между сессиями хранить краткое состояние в `reports/HANDOFF.local.md` (не обязателен; без персональных данных): этап, изменённые файлы, тесты, блокер, следующий шаг. Не копировать туда секреты. Этот файл игнорируется Git.

## B. Экономия при эксплуатации Telegram AI Team (будущая реализация)
1. Проверки прав и антиспам — **до** любого вызова LLM. Простые команды (/help, /privacy и т.п.) — статический ответ; 0 LLM calls.
2. Дешёвый детерминированный роутинг там, где можно; LLM-планировщик — только для неочевидных сложных запросов. Обычно **один** профильный агент на запрос; 2–3 только по реальной необходимости и бюджетному ограничению. Отдельный LLM-синтез не делать, если достаточно объединить ответы без модели.
3. Политика контекста: краткий system prompt роли, запрос пользователя, выбранные выдержки базы знаний, ограниченное окно истории. Отбор по релевантности; не прикреплять весь каталог товаров/весь чат/все навыки.
4. Ограничения: максимальные output tokens, запросы на пользователя/группу, число ролей, вызовы на задачу, таймаут и ограниченный retry. После достижения лимита — корректное сообщение о недоступности вместо бесконечных повторов.
5. Повторное использование данных: кэш для стабильной публичной справки с TTL/версией; не использовать общий кэш для приватных диалогов/чужих персональных данных. Не кэшировать стоимость/наличие без подтверждённого источника и срока актуальности.
6. Учитывать token usage по API при наличии: вход, выход, модель, роль, количество вызовов, тип запроса, метка тарифа. Не записывать raw prompts/PII/секреты в журналы по умолчанию. Финансовые оценки — только по актуальной цене и измеренному usage; не выдумывать рублёвые значения.
7. Использовать модель по сложности задачи с явным качественным тестом; нельзя автоматически утверждать, что меньшая модель безопаснее/дешевле в итоговом сценарии без тестирования. Сложные маркетинговые решения и фактические ответы проверять полноценно.

## C. Проверяемый контроль
- При этапе 00: установить baseline текущих входящих задач/ветвления и примерные объёмы контекстов *без API-вызовов*.
- При этапе 03: тесты на 0 вызовов для простых команд; 1 профильную роль для простого вопроса; ограничение до 3 ролей для сложного; принудительный стоп при лимите и ограниченные retries.
- При этапе 06: сравнение количества вызовов, input/output tokens и качества ответов **на одном наборе задач** до/после. Если экономия не измерена, писать `не измерено`.

**Важно:** Краткость ответа не тождественна экономии входных токенов. Нельзя сокращать реальные данные, имена ключей, требования безопасности, код или точные ошибки для красивых цифр.
